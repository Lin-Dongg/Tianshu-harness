# v3.18.1 发布记录

> 日期：2026-09-11
> 上一版本：v3.18.0（2026-09-11）
> 性质：**修复版**——视觉桥三起故障收口 + Linux AppImage 启动修复 + 图片重试落地。

## 修复（重点条目）

**视觉桥（识图）三起故障收口**

- **运行中配置的识图桥不重启不生效（根修）**：桌面端 sidecar 的会话装配此前恒读启动快照——运行中在 Settings 配好/更换识图桥后，新会话的桥仍然不建，图片被静默丢弃（「配了视觉桥但不能识图」的主诉根因）。现在每次会话装配读取磁盘新配置，**配好桥后下一个新会话即生效，无需重启应用**。
- **推理档视觉模型当桥返回空描述（根修）**：deepseek-flash（4.1 多模态）等推理档模型做识图桥时，中等强度推理在结构化 OCR prompt 下会把 maxTokens 预算全部吃光（实测 reasoning 1717 字符、content 为零），桥返回空描述。桥客户端推理档统一压到 low——工具化描述调用不需要中档推理（实测 reasoning 1717→290 字符，描述正常返回）；非推理档模型（glm-4v-flash 等）行为不变。
- **`image_strip` 剥图重发落地**（issue #94）：413 图片负载超限 / 服务端拒绝图片时，重试此前只是原样重发（必然再次失败）——现在按分类器承诺剥离 `image_url` 后重发一次（保留文本与角色结构），无图可剥或剥后仍失败则快速报错。

**Linux 桌面端**

- **AppImage 启动即崩修复**（issue #80）：剔除包内内置 pango 三库——内置新 pango 需要 harfbuzz ≥3.3 的符号，与 Ubuntu 22.04 及以下的系统 harfbuzz 2.7.4 错配，启动即 symbol lookup error。webkit2gtk 是运行时系统依赖，必然拉入与系统配套的 pango，改走系统配套链后 22.04 正常启动。

## 已知问题

- **MiniMax-M3 视觉上游故障**：MiniMax 服务端当前对 M3 的图片请求返回 500（system error 1033，纯文本正常）——MiniMax-M3 作识图桥暂不可用，非本应用问题。建议改用 glm-4v-flash（免费）/ glm-5.3-flash / deepseek-flash 等视觉模型作桥。
- Linux AppImage 的 3.18.x 包将随下次构建带入 issue #80 修复；3.17.0 包在 Ubuntu 22.04 需按 issue #80 的临时方案（删除内置 pango）启动。

## 升级说明

- 从 **3.16.x / 3.17.x / 3.18.0** 自动更新即可，无配置迁移。
- **3.18.0 用户**：此前配置/更换过识图桥的，升级后新会话自动生效；3.18.0 上的权宜（配桥后重启应用、桥避开推理档模型）在 3.18.1 均不再需要。
